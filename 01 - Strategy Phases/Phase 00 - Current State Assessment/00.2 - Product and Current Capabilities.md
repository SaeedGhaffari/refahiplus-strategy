# 0.2 — محصول و قابلیت‌های فعلی

## هدف

شناخت محصولی که واقعاً پیاده‌سازی شده و تفکیک آن از قابلیت‌های در حال توسعه، ایده‌های آینده و آمادگی عملیاتی اثبات‌نشده.

## ۱. تعریف فعلی محصول

رفاهی‌پلاس یک پلتفرم دیجیتال عرضه خدمات رفاهی و خرید برای کاربران، با تمرکز تجاری اولیه بر سازمان‌هاست. سازمان می‌تواند برای کارکنان اعتبار/کیف پول سازمانی ایجاد کند و استفاده از اعتبار را به دسته‌های مشخص محدود کند.

این توصیف، جهت فعلی محصول را بیان می‌کند و به‌معنای اعتبارسنجی‌شدن تناسب محصول با بازار نیست.

## ۲. ماژول‌ها و اتصال‌های موجود

| حوزه | ماژول/اتصال | وضعیت اعلام‌شده |
|---|---|---|
| هویت و کاربران | Identity | پیاده‌سازی شده |
| اعلان | Notification | پیاده‌سازی شده |
| کیف پول | Wallet | پیاده‌سازی شده |
| سفارش | Order | پیاده‌سازی شده |
| فروشگاه | Store | پیاده‌سازی شده |
| پنل مدیریت | Admin Panel | پیاده‌سازی شده |
| پنل تأمین‌کننده | Supplier Panel | پیاده‌سازی شده |
| پرواز | SnappTrip | اتصال پیاده‌سازی شده |
| هتل | SnappTrip و Lamasoo | اتصال‌ها پیاده‌سازی شده |
| اقامتگاه | Shab | در حال پیاده‌سازی |
| تفریحات | TouristPanel | اتصال پیاده‌سازی شده |
| سینما | iTicket | اتصال پیاده‌سازی شده |
| استخر | Aabsar و PoolTicker | Aabsar پیاده‌سازی شده؛ PoolTicker در حال پیاده‌سازی |
| شارژ و اینترنت | Eniac | اتصال پیاده‌سازی شده |

**محدودیت تفسیر:** «پیاده‌سازی شده» بر اساس اعلام مدیر فنی است و به‌تنهایی اثبات‌کننده تست کامل، پایداری، دسترس‌پذیری عملیاتی، قرارداد معتبر یا امکان فروش واقعی نیست.

## ۳. قابلیت‌های سازمانی و کیف پول

- هر کاربر می‌تواند کیف پول عمومی و چند کیف پول سازمانی داشته باشد.
- مفهوم «عضویت کاربر در گروه» در مدل محصول وجود ندارد.
- گروه در فرایند ادمین صرفاً الگویی برای ایجاد کیف پول‌هایی با محدودیت‌های متفاوت است.
- شماره موبایل کارکنان توسط ادمین وارد می‌شود.
- اگر کاربر از قبل وجود داشته باشد، کیف پول سازمانی جدید برای او ساخته می‌شود.
- محدودیت دسته‌بندی و اعتبار هنگام ساخت کیف پول تعیین می‌شوند و طبق وضعیت فعلی بعداً قابل ویرایش نیستند.
- شارژ گروهی و غیرفعال‌سازی کیف پول‌ها در فرایند مدیریتی وجود دارد.
- مانده اعتبار هنگام خاتمه/غیرفعال‌سازی، مطابق قرارداد سازمان تعیین تکلیف می‌شود؛ بازپرداخت به سازمان یا برداشت مالی در موارد مربوط باید بر اساس منشأ وجه و مفاد قرارداد انجام شود.
- پنل Self-Service اختصاصی سازمان برای مدیریت مستقیم کارکنان/اعتبار گزارش نشده؛ عملیات فعلاً از طریق ادمین انجام می‌شود.

## ۴. پنل‌ها

### پنل مدیریت
مدیریت سرویس‌ها، سفارش‌ها، فروشگاه‌ها، کاربران و کیف پول‌ها.

### پنل تأمین‌کننده
مشاهده/مدیریت سفارش‌ها، پرداخت حضوری، مشاهده موجودی کیف پول‌ها و درخواست برداشت.

جزئیات سطح دسترسی، گردش تأییدها، گزارش‌ها و کنترل‌های مالی باید در تست عملیاتی بررسی شوند.

## ۵. وضعیت استفاده و آمادگی

- محصول برای ورود به تست آماده توصیف شده است؛ تست جامع نهایی انجام نشده.
- استفاده واقعی تجاری توسط مشتریان/کاربران گزارش نشده است.
- استفاده دوستان و آشنایان صرفاً در حد تست بوده و نباید به‌عنوان traction بازار گزارش شود.
- درآمد تجاری وصول‌شده صفر است.
- هنوز شواهد کافی از نرخ موفقیت سفارش، نرخ خطا، پایداری اتصال تأمین‌کننده، تجربه کاربر و عملکرد پشتیبانی وجود ندارد.

## ۶. وابستگی به تأمین‌کنندگان

بخش بزرگی از خدمات از طریق API واسطه‌ها تأمین می‌شود؛ در برخی دسته‌ها همکاری مستقیم محدود نیز وجود دارد. تنوع API از نگاه مدیریت قابل قبول است. این موضوع باید از منظر کیفیت، قیمت، پایداری، پوشش موجودی، SLA، تسویه و امکان جایگزینی ارزیابی شود.

## ۷. شکاف‌های محصول و عملیات

1. تست انتهابه‌انتها برای هر دسته خدمت و سناریوی سفارش.
2. آزمون خطا، timeout، سفارش تکراری، لغو و استرداد.
3. تطبیق وضعیت سفارش رفاهی‌پلاس با وضعیت تأمین‌کننده.
4. کنترل و تطبیق مالی کیف پول، پرداخت، کمیسیون و تسویه.
5. آزمون بار و ظرفیت واقعی.
6. تعریف فرایند پشتیبانی کاربر، سازمان و تأمین‌کننده.
7. تکمیل اتصال‌های در حال توسعه.
8. مشخص‌کردن قابلیت‌های واقعاً قابل عرضه در پایلوت اولیه.

## ۸. شواهد و موارد نیازمند اعتبارسنجی

| موضوع | وضعیت شواهد | اقدام |
|---|---|---|
| وجود ماژول‌ها | اعلام مدیر فنی | تطبیق با نسخه عملیاتی |
| آمادگی عرضه | هنوز اثبات نشده | تست پذیرش و پایلوت کنترل‌شده |
| کیفیت APIها | ارزیابی کلی مدیریت | اندازه‌گیری خطا، latency و قطعی |
| تجربه کاربر | تست جامع گزارش نشده | تست کاربردپذیری |
| قابلیت مقیاس‌پذیری | برآورد فنی موجود | آزمون بار و مانیتورینگ |
| تناسب کیف پول سازمانی | منطق محصول تعریف شده | تست با سازمان و کارکنان |

## ۹. خروجی موردنیاز برای بستن تسک

- ماتریس قابلیت/وضعیت/شواهد هر ماژول
- سناریوهای تست پذیرش
- فهرست محدودیت‌های مانع پایلوت
- فهرست وابستگی‌های تأمین‌کنندگان
- تعریف دامنه نسخه قابل عرضه اولیه

## وضعیت تسک

**وضعیت:** اطلاعات اولیه دریافت شده؛ تست جامع و ممیزی مستقل انجام نشده است.
